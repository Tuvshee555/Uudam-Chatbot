# Conversation Baseline Export

Run from the repository root using Node 22+ and the existing dependencies:

```powershell
node --env-file-if-exists=.env --env-file-if-exists=.env.local --import tsx scripts/export-chatbot-baseline.ts
node --env-file-if-exists=.env --env-file-if-exists=.env.local --import tsx scripts/export-chatbot-baseline.ts --days 7 --limit 100
node --import tsx --test tests/chatbot-baseline.test.ts
```

The exporter uses `NEON_DATABASE_URL`, falling back to `DATABASE_URL`. Prefer a dedicated SELECT-only database credential. No application initialization, schema helpers, demo endpoints, model calls, customer sends, or DB writes run. A dedicated pg client starts with default read-only transactions and executes `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY`; it finishes with `ROLLBACK`. Queries have a 20-second server timeout, a 25-second client timeout, and a 10-second connection timeout. TLS verification is not disabled by the exporter.

Defaults are the previous seven rolling 24-hour periods, ending at export start, and up to 100 conversations. `--days` accepts integers 1-30; `--limit` accepts integers 1-500. Unknown, duplicate, missing, fractional, signed, padded, or out-of-range arguments fail. There is no output-path or customer-ID selector.

Conversations are stored `(platform, sender_id)` threads, randomly ordered for each run before applying the conversation limit. Sampling has no error, success, text-content, or response-presence filter: ordinary replies, problematic replies, and unanswered user messages are eligible together. This permits good and bad outcomes; it does not label or guarantee either. Every stored user and assistant row for each selected thread **within the window** is included, ordered by timestamp then database row ID. No per-thread turn limit applies. Earlier/later history is excluded, so boundary threads can lack context. The database has no session boundary or page-ID field in these rows; this is not a reconstruction of distinct Messenger sessions. Other roles are excluded.

Only sender/platform keys, role, text, and timestamp are read; database IDs are used solely for ordering. Attachments, URLs in attachment fields, customer documents, lead records, and persistent customer memory are never queried. Empty text rows remain empty and are counted; no attachment contents or metadata are inferred. Stored platform can be inaccurate because the application append helper currently omits it and the schema defaults to Facebook.

A fresh 256-bit random run salt creates HMAC pseudonyms. Neither salt nor original keys are written. Pseudonyms cannot be joined across runs. Known sampled sender IDs in text, URLs, email addresses, common credential patterns, and likely Mongolian mobile numbers are replaced before writing. This is best-effort scrubbing, **not anonymization**: text can still contain names, addresses, IDs, other phone formats, or unrecognized secrets. Review and treat the entire artifact as private customer data.

New `travel_messages` top-question analytics entries separately minimize data at insertion: a deterministic identifier from the existing `hashIdentifier` helper is scoped to analytics and platform; email addresses, likely Mongolian mobile numbers, credential-bearing HTTP URLs, PostgreSQL URLs, and common tokens/credential assignments are redacted from text before deriving `norm`. Legitimate trip names/topics, currency prices, ISO departure dates, and public trip links remain. The deterministic analytics hash is unsalted and linkable within its scope, so it is pseudonymization, not anonymization or a secrecy guarantee. Names, addresses, other identifiers/phone formats, unrecognized secrets, and sensitive content in public-looking links can remain. This only affects new analytics inserts: historical analytics rows and conversation history are unchanged; the baseline exporter still reads conversation history and must be handled privately. No historical cleanup or retention change is included.

The JSON artifact is created exclusively as `tmp/chatbot-baseline-<random UUID>.json`, using exclusive create and owner-only file mode on systems that support it. The exporter checks Git ignores that exact path and refuses a symlink/junction or non-directory `tmp`. It offers no arbitrary destination. On Windows, POSIX file modes do not establish NTFS privacy: use a workspace with appropriate account ACLs. Gitignore is not encryption or an access-control boundary. Do not upload, commit, or paste artifacts into chats or tickets; delete them after authorized review using local filesystem tools. Local filesystem administrators can still access them.

Console output contains counts, a generated relative artifact path, and unreviewed status only. Failure output is generic to avoid leaking database exceptions, credentials, raw IDs, or text. The artifact reports eligible and sampled conversation/message counts, user/assistant counts, and empty-text counts. Counts do not establish factual accuracy, delivery, human satisfaction, or a representative quality rate. Inspect both roles in chronological order and annotate quality separately. Missing historical rows, failed persistence, handoffs, and retention can limit review.

Samples above 100,000 messages or 64 MiB of source text abort before fetching message bodies. The final JSON also has a 64 MiB bound; samples are never silently truncated or partially written. Reduce days/limit after a bound failure. Database scans for grouping/random ordering may still be expensive and are limited by statement timeout. Filesystem checks assume a trusted local workspace without concurrent hostile changes.
